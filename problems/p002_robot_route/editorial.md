# Разбор: робот на поле указателей

[Условие](README.md) · [0–1 BFS](solution.py) · [Дейкстра](baseline_dijkstra.py)

## 1. Что переносим из первой главы

Остаются прямоугольное поле, четыре соседа, проверка границ и неявное хранение графа. Меняется вопрос: вместо размера компоненты требуется минимальная стоимость пути между двумя клетками.

Я начинаю с контрпримера к обычному BFS. В поле `RRD / ULL` прямой шаг от верхней левой клетки к нижней левой стоит 1, а обход из пяти шагов стоит 0. Значит, очередность по числу шагов больше не обеспечивает оптимальный ответ.

DSU также не решает новую задачу: структура хранит принадлежность компоненте, но не расстояния и не маршрут. Для стоимости движения нужно учитывать направленные рёбра.

## 2. Граф и веса

Каждая проходимая клетка — вершина. В каждую соседнюю проходимую клетку можно перейти; вес зависит от направления и указателя **клетки отправления**:

```python
weight = int(grid[row][col] != direction)
```

Стрелка в клетке назначения не определяет цену входа. Она понадобится лишь при следующем выходе из этой клетки. Старт ничего не стоит сам по себе; вес платится за переход.

У каждой вершины максимум четыре исходящих ребра. Поэтому при `N=n*m` имеем `V<=N`, `E<=4N`. Явный список всех рёбер в основном алгоритме не нужен.

## 3. Почему именно 0–1 BFS

Дейкстра подходит для этих весов, поскольку они неотрицательны. Но в нашем случае любое улучшение из слоя `d` ведёт только в слой `d` или `d+1`. Эту структуру можно поддержать через `deque`: бесплатный переход отправляет запись в начало, платный — в конец.

Усложнение относительно обычного BFS состоит не только в дополнительном методе очереди. Вместо отметки «посещено» храним лучшую найденную стоимость, допускаем её улучшение, сохраняем предшественника и отбрасываем устаревшие записи.

## 4. Структура кода

| Часть | Роль |
|---|---|
| `DIRECTIONS` | Четыре смещения и соответствующие символы |
| `find_route` | Поиск оптимальной стоимости и маршрута |
| `distance` | Лучшие найденные стоимости |
| `parent` | Предшественники для восстановления |
| `queue` | Пары «сохранённая стоимость, номер клетки» |
| `solve` | Чтение координат с единицы и формат ответа |
| `minimum_cost_dijkstra` | Независимая проверка стоимости через кучу |

### Подготовка

Координаты переводятся в номера `row*cols+col`. Старт получает расстояние 0; остальные клетки — маркер бесконечности. У всех `parent=-1`, поэтому цепочка предшественников остановится после старта.

В качестве бесконечности достаточно `N+1`: оптимальный простой путь имеет максимум `N-1` переходов, каждый стоит не больше 1. Это обоснованный предел, а не случайная большая константа.

### Извлечение

Из начала очереди получаем пару `(current_distance, cell)`. Если расстояние в паре отличается от текущего `distance[cell]`, запись устарела. Пропускаем её до обработки соседей и до проверки цели.

Если актуальная запись относится к цели, можно завершить поиск: её минимальная метка уже окончательна. Завершать поиск при первом обнаружении цели нельзя.

### Релаксация

Для каждого допустимого соседа считаем `candidate=current_distance+weight`. Только строго меньшее значение заменяет прежнее расстояние и предшественника.

Если `weight==0`, новая запись добавляется слева; иначе — справа. Ни посещённость в момент первого обнаружения, ни стоимость клетки назначения вместо отправления здесь не подходят.

### Ответ и путь

Если цель сохранила бесконечное расстояние, возвращаем `(-1, [])`. Иначе идём по `parent` от цели до `-1`, добавляем координаты, разворачиваем список. В `solve` возвращается нумерация с единицы.

Путь может быть длиннее другого пути той же стоимости: задача не содержит дополнительного критерия по числу шагов.

## 5. Как исправляется первое неудачное обнаружение

Возьмём поле:

```text
RD
UL
```

Старт — `(1,1)`, цель — `(2,1)` в нумерации условия. Направления в коде перечислены как `U, D, L, R`.

| Действие | Метка цели | Что происходит |
|---|---|---|
| Из старта рассматриваем шаг вниз | 1 | Цель добавляется справа |
| Из старта рассматриваем шаг вправо | 1 | Правая верхняя клетка с меткой 0 добавляется слева |
| Идём вниз по `D` | 1 | Правая нижняя клетка получает 0 и идёт слева |
| Идём влево по `L` | 0 | Цель улучшается и добавляется слева |
| Извлекаем актуальную цель | 0 | Завершаем с бесплатным путём |

Старая запись цели с меткой 1 могла остаться в очереди, но она не влияет на ответ. Если продолжать поиск всех расстояний, её пропустит проверка устаревшей метки.

## 6. Доказательство корректности

**Допустимость модели.** Каждому разрешённому шагу соответствует ребро в неявном графе с той же стоимостью. Любая цепочка таких рёбер задаёт разрешённый маршрут. Следовательно, поиск минимального пути в графе эквивалентен задаче управления роботом.

**Реальность меток.** Изначально метка 0 соответствует пустому пути в старт. Каждая релаксация продолжает уже найденный путь одним допустимым ребром, поэтому всякая конечная метка — стоимость некоторого реального пути.

**Порядок обработки.** При извлечении стоимости `d` все записи текущего слоя стоят раньше следующего. Добавления слева имеют ту же стоимость `d`, добавления справа — `d+1`. Пропуск старых записей не нарушает порядок. Поэтому каждая актуальная обработка выбирает минимальную оставшуюся стоимость.

**Окончательность.** Если бы актуально извлечённая вершина имела более дешёвый путь, на этом пути существовала бы первая ещё не обработанная вершина после уже обработанного предшественника. Релаксация от предшественника дала бы ей меньшую метку, которая должна была бы извлечься раньше. Получаем противоречие. Значит, актуальная метка цели оптимальна.

**Восстановление.** Родитель сохраняется при строгом улучшении от окончательно обрабатываемой вершины. Назначение не создаёт цикл в цепочке родителей: новый путь продолжается из уже окончательной вершины к ещё не окончательной. Пройденные рёбра соответствуют сохранённым релаксациям. После разворота получаем простой допустимый путь от старта к цели с найденной стоимостью.

Если цель недостижима, релаксация никогда не присвоит ей конечную метку. Если достижима, перебор рёбер от достижимых вершин рано или поздно обнаружит её. Поэтому ответ `-1` также корректен.

## 7. Время и память

Для 0–1 BFS время — `O(V+E)`. На сетке это **`O(N)`**. Расстояния, предшественники и очередь занимают **`O(N)`** памяти; маршрут длиной `k` требует `O(k)` памяти и времени на восстановление. Поскольку `k<=N`, общая граница остаётся линейной.

Ввод и формирование ответа тоже линейны по объёму данных. `solve` хранит строки ответа и объединённый текст; это увеличивает практический расход памяти, хотя не меняет асимптотику. Для жёсткого лимита можно печатать координаты порциями.

Дейкстра на той же сетке работает за `O(N log(N+1))` и использует `O(N)` памяти. Его роль здесь — показать общий принцип и дать независимый проверочный алгоритм.

## 8. Ошибки, которые проверяют тесты

| Ошибка | Контрпример или последствие |
|---|---|
| Обычный BFS по шагам | Прямой платный шаг хуже длинного бесплатного обхода |
| Отметить клетку навсегда при добавлении | Первая метка цели 1 не улучшается до 0 |
| Остановиться при добавлении цели | Преждевременный ответ в том же примере |
| Смотреть стрелку назначения | В строке `RR` обратный переход ошибочно становится бесплатным |
| Использовать `<=` | Бесконечные равные обновления на нулевом цикле |
| Разрешить шаг по стрелке в стену | Получается недопустимый маршрут |
| Путать число клеток и шагов | Для старта, равного цели, должен выводиться один элемент |
| Требовать одинаковый путь от двух алгоритмов | Разные оптимальные маршруты ошибочно считаются расхождением |

## 9. Проверка решения

В [`tests/test_robot_route.py`](../../tests/test_robot_route.py) стоимость основного решения сверяется двумя способами:

- полный перебор всех `5^4=625` полей 2×2 из `UDLR#`, для каждого — все пары проходимых стартов и целей; эталон — Беллман–Форд с явным списком рёбер;
- 1000 воспроизводимых случайных полей до 7×7; эталон — Дейкстра с другой организацией расстояний и очереди.

Каждый возвращённый маршрут отдельно проверяется: начало и конец, границы, отсутствие стен и повторов, соседство клеток и точная сумма команд. Есть проверки примеров, запуска из командной строки и пути из 200 000 клеток. Такой длинный маршрут восстанавливается циклом, без зависимости от лимита рекурсии Python.

Беллман–Форд в тестах — малый проверочный инструмент, а не рекомендуемое решение полного ограничения. Он последовательно релаксирует все рёбра до `V-1` раз: этого хватает для всех простых путей. Отрицательных рёбер в наших тестируемых графах нет.

## 10. Подсказки к упражнениям

1. Можно убрать `parent` и список пути. Асимптотическая память останется `O(N)` из-за расстояний и очереди, но константа уменьшится.
2. Нужен обычный BFS. В первом примере кратчайший по шагам путь состоит из одного перехода вниз, даже если он стоит одну команду.
3. Веса 0 и 7 можно нормировать до 0 и 1. Число команд из 0–1 BFS умножается на 7; путь остаётся оптимальным.
4. Для произвольных неотрицательных цен подходит Дейкстра: на сетке `O(N log(N+1))` времени. Верхнюю границу бесконечности тоже нужно заменить или пересчитать.
5. Уберите ранний выход по цели, завершите очередь и верните весь массив расстояний. Для внешнего интерфейса можно заменить маркер бесконечности на `-1`.
6. Дейкстра по парам `(стоимость, шаги)` с лексикографическим сравнением решает два критерия. Каждый переход прибавляет `(w, 1)`; в куче нужен соответствующий приоритет, а не только стоимость.
