# Разбор: фрагмент журнала событий

[Условие](README.md) · [Решение](solution.py) · [Эталон](baseline_bruteforce.py)

## Модель и базовая идея

Я рассматриваю журнал как последовательность типов. Нужно выбрать непрерывный интервал с ограниченной мощностью множества его значений. Повторения одного типа не расходуют новые места в лимите.

Простой эталон перебирает каждый старт и расширяет правый конец, поддерживая множество. Когда типов стало больше `k`, дальнейшее расширение при том же старте бесполезно. Это ожидаемое `O(n²)` времени и `O(n)` памяти в худшем случае. Код эталона не использует общую левую границу и частоты, поэтому подходит для независимого сравнения.

## Что оптимизируем

Не нужно начинать подсчёт заново для каждого старта. Храним частоты текущего окна и передвигаем его границы только вправо. После добавления события удаляем слева ровно столько событий, сколько нужно для восстановления ограничения.

| Часть программы | Назначение |
|---|---|
| `longest_window` | Возвращает оптимальные границы `[left,right)` с нуля |
| `counts` | Положительные частоты текущего окна |
| `left` | Начало текущего допустимого окна после сжатия |
| `best_left`, `best_right` | Границы лучшего найденного ответа |
| `solve` | Читает ввод и переводит границы в формат условия |
| `longest_window_bruteforce` | Проверочный квадратичный алгоритм |

## Структура решения

1. Изначально словарь и лучший ответ пусты.
2. `enumerate` даёт индекс правого события и его тип.
3. Увеличиваем частоту этого типа.
4. Если типов больше лимита, уменьшаем частоту `events[left]`, удаляем нулевой ключ и увеличиваем `left`. Повторяем до допустимости.
5. Длина текущего окна равна `right+1-left`.
6. Только строгое увеличение длины заменяет лучший ответ.
7. Возвращаем границы; пустое окно печатается специальным образом.

При `k=0` каждое добавленное событие сразу удаляется. Текущее окно пусто, лучший ответ остаётся `(0,0)`. Отдельная ветка внутри алгоритма для этого не нужна.

## Доказательство

Словарь точно описывает окно, потому что каждый сдвиг границы сопровождается соответствующим изменением одной частоты. После сжатия все частоты положительны, поэтому `len(counts)` — точное число типов.

Для каждого правого конца алгоритм сохраняет самый ранний допустимый старт. Все более ранние старты уже нарушили ограничение, а расширение вправо не может уменьшить количество типов. Значит, текущее окно — самое длинное для этого конца. Максимум по всем правым концам совпадает с глобальным оптимумом. При равенстве длин первый найденный вариант имеет более ранние границы и сохраняется строгим сравнением.

Развёрнутый инвариант и аргумент сложности находятся в [теории](../../theory/04_window_invariants.md) и [главе алгоритма](../../algorithms/08_sliding_window.md).

## Сложность

Правый указатель делает `n` шагов, левый суммарно не больше `n`. Поэтому ожидаемое время — `O(n)` при стандартной модели операций хеш-таблицы. Дополнительная память вычислительной функции — `O(min(n,k+1))`; память всей программы со входом — `O(n)`.

Идентификаторы достигают `10^9`, поэтому массив частот на весь диапазон значений непрактичен. Словарь хранит только текущие типы. Если бы алфавит был мал и заранее известен, массив частот мог бы дать детерминированное константное обновление без хеширования.

## Ошибки и проверки

| Ошибка | Последствие |
|---|---|
| Множество вместо частот при удалении | Тип исчезает слишком рано, хотя его копия остаётся |
| `if` вместо `while` для сжатия | Окно может остаться недопустимым |
| Не удалять нулевые ключи | Число типов вычисляется неверно |
| Обновлять при `>=` | Поздний ответ заменяет ранний при равенстве |
| Копировать и пересчитывать каждый срез | Линейная идея превращается в квадратичную реализацию |
| Смешать включительную и исключительную границы | Ошибка на единицу в длине и выводе |

В [тестах](../../tests/test_event_window.py) проверяются все 3280 последовательностей длины 0–7 над тремя значениями, для каждой — лимиты 0–4. Дополнительно: 1000 случайных случаев, равенства, многократное сжатие, нулевой лимит, сохранение входа, примеры и CLI. Два больших случая по 200 000 событий проверяют расширение без сжатия и постоянное сжатие.

Сравнение идёт по полной паре границ, а не только по длине: так проверяется и правило выбора самого раннего ответа.

## Подсказки к упражнениям

1. Для самого позднего варианта обновляйте при равной длине тоже, отдельно сохраняя соглашение о пустом ответе.
2. После добавления типа сжимайте окно, пока его частота больше 1; остальные типы до этого уже были уникальны.
3. Для каждого правого конца после сжатия допустимы все старты от `left` до `right`. Добавляйте `right-left+1` к счётчику.
4. Для `k>=1` ответ равен `at_most(k)-at_most(k-1)`. Для ровно нуля типов непустых фрагментов нет.
5. Окно с меньшим числом типов допустимо для «не более», но не для «ровно». Обновляйте максимум только когда число типов равно `k`; случай `k=0` отдельно пустой.
6. Нет общего переноса: `[5,-2]` при лимите суммы 3 показывает, что временное нарушение может исправиться расширением. Нужен иной подход, зависящий от новой постановки.
