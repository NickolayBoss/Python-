## Три запроса, три способа подготовки

| Запрос | Что храним | Время ответа |
|---|---|---|
| Сумма | Префиксные суммы с начальным нулём | O(1) |
| Частота кода | Список позиций для каждого кода | O(log(n + 1)) |
| Самый длинный фрагмент | Максимум, найденный скользящим окном | O(1) |

**Сумма.** Префикс `totals[r]` содержит записи до `r`. Вычитание `totals[l]` убирает записи до `l`. Например, для значений 5, −3, 8 первые четыре префикса равны 0, 5, 2, 10.

**Частота.** Позиции кода 4 в примере — 0 и 2. Бинарный поиск границы для `l = 1` даёт индекс 1 в списке позиций, а для `r = 6` — индекс 2. Разность равна 1. Позиция ровно `r` исключается, поскольку обе границы вычисляются через `bisect_left`.

**Окно.** Добавляем правую запись и сдвигаем левый край, пока кодов больше `k`. Удаляем из словаря коды с нулевой частотой. После сдвигов левый край — самый ранний допустимый для текущего правого. Любая пропущенная левая граница давала слишком много кодов, а добавление записей справа не уменьшает их число. Максимум по всем правым границам даёт искомую длину.

Подготовка занимает O(n) времени в среднем с учётом операций словаря и O(n) памяти. Каждый указатель проходит журнал один раз. CLI дополнительно хранит O(q) строк ответа.

## Самопроверка

1. Почему для частоты нельзя просто вычесть два элемента общего префикса сумм?
2. Что вернёт окно при `k = 0` и почему оно останется пустым?
3. Как вернуть границы самого раннего максимального окна?
4. Что пришлось бы пересчитывать при изменении кода записи?
