# Разбор: очередь рендер-фермы

[Условие](README.md) · [Основное решение](solution.py) · [Эталон](baseline_bruteforce.py)

## 1. Модель и отличие от предыдущих глав

В первых двух задачах мы работали с графами. Теперь вход — последовательность положительных длительностей, а решение — выбор границ между соседними заданиями. Максимум сумм блоков нужно минимизировать: это задача типа **minimax**.

Я сохраняю исходный порядок и ищу время завершения, а не конкретное назначение серверов. Любое разбиение на `g<=k` блоков можно назначить `g` одинаковым серверам. Поскольку они запускаются одновременно, итоговое время равно самой большой нагрузке.

## 2. Базовый способ: перебрать разрезы

Между заданиями есть `n-1` возможных границ. Для ровно `k` блоков выбираем `k-1` границ, считаем суммы блоков и максимум. Лучший из максимумов — оптимум для такого числа блоков.

Почему эталон перебирает ровно `k`, если условие разрешает меньше? Если разбиение использует меньше `k` блоков, а `k<=n`, можно разделить один из блоков, содержащих несколько заданий. При положительных длительностях суммы новых блоков не превосходят прежнюю. Повторяя разделение, получаем ровно `k` блоков без увеличения максимума. Поэтому минимумы совпадают.

В `baseline_bruteforce.py` суммы считаются префиксами, границы перебираются через `combinations`, соседние границы — через `pairwise`. При `B=C(n-1,k-1)` время составляет `O(n+kB)`, дополнительная память — `O(n+k)`. Это независимый проверочный алгоритм для малых данных, а не решение ограничения 200 000.

## 3. Перейти от оптимума к допустимости

Зададим лимит `T` и спросим: можно ли уложиться в него на `k` серверах? Если можно при `T`, можно и при большем лимите. Получили монотонный предикат.

Нижняя граница ответа — `max(durations)`, верхняя — `sum(durations)`. Бинарный поиск найдёт первую допустимую точку, если проверка работает правильно.

## 4. Проверка одного лимита

`can_finish` хранит два числа:

| Переменная | Значение |
|---|---|
| `used` | Число уже открытых блоков |
| `current` | Сумма последнего блока |

Новое задание добавляется в последний блок, пока сумма не превышает лимит. Иначе оно начинает новый блок. Если количество блоков стало больше `workers`, проверка завершается с `False`. Если одно задание превышает лимит само по себе, сразу возвращается `False`.

Например, при `T=17` очередь `[7,2,5,10,8]` даёт `[7,2,5] | [10] | [8]`, то есть три блока. При `T=18` последние два задания помещаются вместе, нужны два блока.

Почему нельзя взять менее жадную границу и получить меньше блоков? После любого количества блоков жадный алгоритм продвинулся не меньше, чем любое другое допустимое разбиение. Это свойство подробно доказано в [отдельной главе](../../algorithms/07_greedy_partition.md). Значит, полученное число блоков минимально для выбранного лимита.

## 5. Структура реализации

| Функция | Ответственность |
|---|---|
| `can_finish` | Точная проверка одного кандидата за один проход |
| `minimum_time` | Границы и бинарный поиск минимального допустимого времени |
| `solve` | Разбор корректного ввода и формирование строки ответа |
| `minimum_time_bruteforce` | Независимый полный перебор на малых входах |

В `minimum_time` на допустимом кандидате выполняется `right=middle`, на недопустимом — `left=middle+1`. Поиск останавливается при совпадении границ. Отдельный массив значений предиката не строится, исходный список не сортируется и не изменяется.

## 6. Полное доказательство корректности

**Лемма о жадной проверке.** Для заданного лимита жадное продление каждого блока вправо использует минимальное количество блоков. Доказательство по числу блоков: первый жадный блок достигает максимально возможной границы; если предыдущая жадная граница не левее границы другого разбиения, его следующий блок может покрыть оставшийся суффикс соответствующего блока другого разбиения, поскольку длительности неотрицательны. Следовательно, жадная граница снова не левее.

**Следствие.** `can_finish` возвращает истину тогда и только тогда, когда существует разбиение на не больше `k` блоков с суммой каждого не больше лимита. Если жадному нужно больше `k`, никакое другое разбиение не уложится; если не больше, построенные блоки сами служат допустимым вариантом.

**Монотонность.** Любое допустимое разбиение при лимите `T` остаётся допустимым при увеличении лимита. Значит, после первой истины предикат больше не становится ложным.

**Поиск.** В начале минимум лежит в `[max(a),sum(a)]`. При истинной середине минимум не правее неё; при ложной — строго правее. Обновления сохраняют ответ внутри интервала и уменьшают интервал. В конце его единственное значение — минимально допустимое время.

Эти утверждения вместе доказывают корректность возвращаемого ответа.

## 7. Сложность и ограничения

Обозначим `S=sum(a)`, `R=S-max(a)+1`. Вычисление границ занимает `O(n)`. Каждая проверка — `O(n)`, число проверок — `O(log R)`. Итого **`O(n(1+log R))` времени**, или более простая верхняя оценка `O(n log(S+1))`.

Проверка и поиск используют **`O(1)` дополнительной памяти** поверх списка длительностей. Программа целиком хранит вход, токены и список чисел: её общая память **`O(n)`**. Важно отличать память алгоритма поверх входа от памяти всей программы.

При максимальном входе сумма не больше `2*10^14`; для исходного диапазона потребуется не более 48 проверок. Python справляется с такой суммой без фиксированного 32-битного переполнения. Тест на большом входе проверяет работоспособность, но не гарантирует произвольный лимит онлайн-судьи.

## 8. Типичные ошибки

| Ошибка | Что ломается |
|---|---|
| Сортировка длительностей | Меняется порядок и множество разрешённых разбиений |
| Сравнение `current + duration >= limit` | Ровно заполненный блок ошибочно разделяется |
| `current=0` при открытии блока | Теряется первое задание нового блока |
| `left=middle` в выбранном шаблоне | Поиск может зациклиться |
| `right=middle-1` на истине | Можно исключить минимальный ответ |
| Отсутствие проверки `duration > limit` | Отдельная функция допустимости может принять слишком маленький лимит |
| Ответ как средняя нагрузка | Игнорируется неделимость и непрерывность блоков |
| Использование полного перебора на больших данных | Экспоненциальное число разрезов |

## 9. Проверки

В [`tests/test_render_batches.py`](../../tests/test_render_batches.py) есть 15 тестовых методов:

- три примера и запуск программы из командной строки;
- одно задание, один сервер, сервер для каждого задания;
- точное равенство лимиту, сохранение порядка, большие суммы;
- все массивы длины от 1 до 6 со значениями 1–3, для каждого — все допустимые количества серверов; всего 1092 массива;
- 1000 случайных входов с фиксированным seed `20261111`, сравнение с перебором разрезов;
- проверка границы: ответ допустим, ответ минус один недопустим;
- монотонность предиката и неувеличение ответа при добавлении серверов;
- очередь из 200 000 заданий.

На малых входах независимый эталон не использует ни бинарный поиск, ни жадную проверку, поэтому сравнение проверяет обе ключевые части решения.

## 10. Подсказки к упражнениям

1. После поиска лимита повторите жадный проход, сохраняя границы блоков. Получите не больше `k` блоков с оптимальным максимумом.
2. Минимум не изменится: можно дробить блоки до ровно `k`, не увеличивая их суммы. Если нужно вывести разбиение, потребуется учесть дополнительное дробление.
3. `[2,3] | [5]` подходит; равенство лимиту допустимо, поэтому новый блок открывается только при превышении.
4. Монотонность, жадное доказательство и границы сохраняются. Если все длительности нулевые, границы сразу совпадут в нуле и поиск не запустится.
5. `[6,-2]` при лимите 4 допускает один блок, но проверка отвергнет задание 6. Ограничения положительности нельзя убирать без нового анализа.
6. При лимите времени `T` проверяйте суммы блоков против `T-s`. Границы времени можно взять от `max(a)+s` до `sum(a)+s`, предполагая `s>=0` и параллельный запуск серверов.
7. Средняя нагрузка — нижняя оценка, но достичь её могут помешать неделимость и фиксированный порядок. Первый пример даёт ответ 18 вместо 16.
