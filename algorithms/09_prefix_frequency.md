# Подсчёт фрагментов через частоты префиксов

[Алгоритмы](README.md) · [Теория](../theory/05_prefix_sums.md) · [Реализация](../problems/p005_balance_segments/solution.py)

## Шаги

1. Создаём `frequencies={0:1}`, текущую сумму 0 и ответ 0.
2. Читаем очередное изменение и прибавляем к текущему префиксу.
3. Ищем число предыдущих префиксов со значением `prefix-target`.
4. Прибавляем это число к ответу.
5. Увеличиваем частоту текущего префикса.

Все пункты выполняются за один проход. Отдельный массив префиксов не нужен.

## Трассировка первого примера

| Операция | Префикс | Искомый префикс при цели 3 | Найдено раньше | Накопленный ответ |
|---|---|---|---|---|
| 2 | 2 | -1 | 0 | 0 |
| -1 | 1 | -2 | 0 | 0 |
| 2 | 3 | 0 | 1 | 1 |
| 1 | 4 | 1 | 1 | 2 |
| -2 | 2 | -1 | 0 | 2 |

После каждого запроса текущая сумма добавляется в частоты.

## Инвариант и доказательство

Перед обработкой элемента с номером `r` (с единицы) словарь хранит частоты ровно `P[0]...P[r-1]`. Изначально это один пустой префикс, поэтому утверждение верно.

После прибавления элемента вычислено `P[r]`. Каждый ранее встреченный `P[l]=P[r]-s` задаёт ровно один непустой период `[l,r)` нужной суммы. Другие префиксы таких периодов не задают. Добавленная частота поэтому равна числу всех подходящих периодов с этой правой границей.

Затем записываем `P[r]` в словарь, восстанавливая инвариант перед следующим элементом. Каждый период учитывается ровно на своей правой границе. Следовательно, итоговый ответ точен.

## Почему нужна частота, а не set

В `[0,0,0]` каждый префикс равен 0. Число новых ответов на шагах равно 1, 2 и 3. Множество хранит только наличие нуля и не различает возможные левые границы: оно дало бы 3 вместо 6.

## Порядок обновления

Если сначала добавить текущий префикс, при цели 0 поиск обнаружит его же и посчитает пустой период `[r,r)`. На каждом шаге появится один лишний ответ. Поэтому запрос обязательно предшествует обновлению частоты.

## Сложность

При стандартной модели хеширования словарные операции имеют ожидаемую константную стоимость. Получаем **ожидаемое `O(n)` времени**, **`O(n)` дополнительной памяти**: различных префиксов не более `n+1`. Это не детерминированная линейная худшая оценка при произвольных коллизиях.

Алгоритм поддерживает поток значений и не требует сохранять исходные операции. Однако словарь сам может линейно расти: потоковый интерфейс не означает константную память.

## Варианты задачи

Для самого длинного периода сохраняют первый индекс каждого префикса, для самого короткого — последний. Для количества сохраняют частоту. Одно уравнение может требовать разных данных в словаре в зависимости от искомого результата.
