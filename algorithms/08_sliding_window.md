# Два указателя и скользящее окно

[Алгоритмы](README.md) · [Инварианты](../theory/04_window_invariants.md) · [Код](../problems/p004_event_window/solution.py)

## Алгоритм для не более k типов

1. Создаём пустой словарь частот, левую границу и пустой лучший ответ.
2. Перебираем события правым указателем.
3. Добавляем событие в частоты.
4. Пока типов больше `k`, удаляем одно событие слева и сдвигаем левую границу.
5. Удаляем ключ, если его частота стала нулевой.
6. Для допустимого окна сравниваем длину с лучшей.
7. При строгом улучшении сохраняем границы.

Слово «пока» существенно: один сдвиг может убрать лишь одну копию типа, не уменьшив число разных типов.

## Трассировка

Для `[1,2,1,3]`, `k=2`:

| Правый индекс с нуля | Добавлено | Левый индекс после сжатия | Окно | Частоты |
|---|---|---|---|---|
| 0 | 1 | 0 | `[1]` | `{1:1}` |
| 1 | 2 | 0 | `[1,2]` | `{1:1,2:1}` |
| 2 | 1 | 0 | `[1,2,1]` | `{1:2,2:1}` |
| 3 | 3 | 2 | `[1,3]` | `{1:1,3:1}` |

На последнем шаге удалить первый элемент недостаточно: тип 1 остаётся. Нужно удалить и тип 2. Ранее найденное окно длины 3 сохраняется.

## Выбор при равенстве

Обновляем ответ только при `new_length > best_length`. Правые концы просматриваются по возрастанию; для равных длин более ранний правый конец означает и более ранний старт. Поэтому первая найденная максимальная длина даёт требуемый самый ранний фрагмент.

## Корректность

При добавлении справа словарь увеличивает ровно одну частоту, при удалении слева уменьшает ровно одну; нулевые ключи убираются. Значит, он точно описывает окно.

Любой старт левее сохранённой границы был отвергнут из-за избытка типов на этом или более раннем шаге. Добавление событий не могло исправить нарушение. Сжатие останавливается сразу после восстановления допустимости. Следовательно, текущий старт — самый ранний подходящий и окно максимально по длине для этого правого конца.

Любой глобально оптимальный фрагмент имеет некоторый правый конец. На соответствующем шаге алгоритм рассматривает окно не короче него. Поэтому максимальная найденная длина оптимальна, а строгое обновление корректно разрешает равенства.

## Время и память

Каждое событие добавляется один раз и удаляется не более одного раза. При стандартной модели хеширования получаем **ожидаемое `O(n)` времени**. Это не безусловная худшая оценка для произвольных коллизий хеш-таблицы.

После сжатия в словаре максимум `k` ключей, временно перед сжатием — максимум `k+1`. Дополнительная память — `O(min(n,k+1))`. Сам вход хранится отдельно, и программа целиком требует `O(n)` памяти.

## Отличие от предыдущей главы

В задаче 003 мы несколько раз проверяли всю очередь при разных лимитах. Здесь нужная граница окна обновляется непосредственно за один проход. Бинарный поиск по длине тоже возможен с подходящей проверкой, но дал бы лишний логарифмический множитель. Выбирать нужно подход по структуре условия, а не повторять последний изученный алгоритм.
